# From a Paper to a Reusable Local ENA Dataset

*An end-to-end tutorial for ENA Project Archiver 0.1.1*

A paper catches your attention because its sequencing data could answer a question of your own. Perhaps you want to reanalyse an RNA-seq experiment with a newer reference genome, include published genomes in a population-genetic comparison, or simply preserve an important dataset locally before building a computational workflow around it.

Near the end of the paper you find an accession such as `PRJEB2772`.

At first sight the rest seems easy: go to ENA and download the FASTQ files.

That approach works until the dataset becomes scientifically important.

Six months later you may want to know which files ENA actually offered at the time, whether the FASTQ files were the objects originally submitted by the authors or versions generated by ENA, which Sample belonged to which Run, whether the repository subsequently changed a file, and whether the 40 GB file sitting on disk really completed its download.

`ena-project` is intended to make that transition from *an accession in a paper* to *a dataset you can confidently reuse* more systematic.

Its view of an ENA dataset is:

```text
paper or database search
        ↓
BioProject / Study accession
        ↓
preserved ENA metadata
        ↓
complete inventory of available files
        ↓
explicit decision about which representation to keep
        ↓
verified local files
```

This distinction matters particularly at ENA because a Run can have several representations. The original submitted files may be available, ENA may provide standardized FASTQ, and an SRA representation may also exist. These are useful for different reasons and need not be byte-for-byte versions of the same object.

The tutorial begins with the cautious workflow I would recommend to a computational biologist encountering a new project for the first time. Later sections use realistic situations to explain why the other commands exist.

As a worked example we will use the real ENA project `PRJEB2772`, a wheat starchy-endosperm RNA-seq dataset. The project's own live smoke test resolves it to Study `ERP001030` and finds five Samples, five Experiments and five Runs. It is small enough at the metadata level to make a convenient example, but **do not assume any public dataset is small enough to download casually**. The dry run exists for precisely that reason.

## 1. Install a specific release

For scientific software, installing a known release is preferable to installing whatever happens to be on the development branch that day.

Create a small Python environment:

```bash
python3 -m venv ~/.venvs/ena-project
source ~/.venvs/ena-project/bin/activate

python -m pip install --upgrade pip
python -m pip install \
  "git+https://github.com/costantinicarlo/ena-project-archiver.git@v0.1.1"
```

Confirm the installation:

```bash
ena-project --help
```

The application requires Python 3.9 or newer and uses `curl` for sequence transfers.

If you prefer to work from a checkout:

```bash
git clone --branch v0.1.1 --depth 1 \
  https://github.com/costantinicarlo/ena-project-archiver.git

cd ena-project-archiver
python3 -m venv .venv
source .venv/bin/activate
python -m pip install .
```

Using the tag here is deliberate: it makes the tutorial reproducible even after development continues.

## 2. Give the dataset a durable home

Suppose you maintain public sequencing projects beneath:

```text
/data/bioprojects/
```

or, on macOS:

```text
/Volumes/Bioinfo-1/BIOPROJECTS/
```

Repository provenance is worth making visible. ENA and NCBI can expose the same INSDC project while not necessarily exposing the same physical archival objects.

A useful layout is therefore:

```text
BIOPROJECTS/
└── PRJEB2772/
    └── sources/
        └── ena/
```

Set a few shell variables:

```bash
PROJECT="PRJEB2772"
OUTDIR="/Volumes/Bioinfo-1/BIOPROJECTS/$PROJECT/sources/ena"
```

On Linux you might instead use:

```bash
OUTDIR="/data/bioprojects/$PROJECT/sources/ena"
```

Do not create a directory under `/Volumes` merely because you expect a disk to be mounted there. Let the application check the destination when it starts.

## 3. First use case: “I found this project, but I am not yet sure I want the data”

This is what the `metadata` command is for.

You have an accession, but before allocating hundreds of gigabytes you want to know what the project actually contains.

Run:

```bash
ena-project metadata "$PROJECT" \
  --outdir "$OUTDIR"
```

No sequence data are downloaded and no acquisition representation is chosen.

Instead, the command preserves the ENA responses and constructs a local description of the project.

The most useful files are:

```text
metadata/
├── snapshot.json
├── raw/
│   ├── portal/
│   └── xml/
└── derived/
    ├── project.json
    ├── samples.tsv
    ├── sample_attributes.tsv
    ├── experiments.tsv
    ├── runs.tsv
    └── files.tsv
```

Start with the project identity:

```bash
python -m json.tool \
  "$OUTDIR/metadata/derived/project.json" | less
```

Then inspect the Runs:

```bash
column -t -s $'\t' \
  "$OUTDIR/metadata/derived/runs.tsv" | less -S
```

For biological provenance, the Sample table is often more interesting:

```bash
column -t -s $'\t' \
  "$OUTDIR/metadata/derived/samples.tsv" | less -S
```

and ENA Sample attributes that do not fit comfortably into a fixed table are retained separately:

```bash
column -t -s $'\t' \
  "$OUTDIR/metadata/derived/sample_attributes.tsv" | less -S
```

This is the point at which you should compare the repository with the paper.

Are these the organism and tissues you expected? Does the library strategy agree with the Methods? Are there five Runs because the experiment really had five sequencing libraries, or did you expect twenty? Is this actually RNA-seq, whole-genome sequencing, amplicon sequencing, or something else?

The software can tell you what ENA says. It cannot decide whether that dataset is the one your scientific question requires.

## 4. Validate the metadata before trusting it

Because no sequence files exist yet, use metadata-only validation:

```bash
ena-project validate "$OUTDIR" --metadata-only
```

This checks the internal structure of the snapshot, checks the local SHA-256 ledger for metadata files, and verifies relationships between Samples, Experiments, Runs and the file inventory.

A Browser XML request can occasionally fail while the essential Portal inventory remains usable. Such a snapshot is recorded explicitly as `partial` rather than being presented as complete. Read:

```bash
python -m json.tool \
  "$OUTDIR/metadata/snapshot.json" | less
```

if the command returns status `4` or reports a warning.

A partial optional XML harvest and a malformed Run inventory are not the same thing. The latter is a reason to stop.

---

## 5. The file that makes ENA different: `files.tsv`

Now inspect:

```bash
column -t -s $'\t' \
  "$OUTDIR/metadata/derived/files.tsv" | less -S
```

This file is **not a download list**.

It is an inventory of the physical raw-read objects ENA reported as available.

A quick representation count is:

```bash
tail -n +2 "$OUTDIR/metadata/derived/files.tsv" |
  cut -f8 |
  sort |
  uniq -c
```

Depending on the project, you may see:

```text
submitted
fastq
sra
```

Why retain all of this before choosing what to download?

Imagine that the authors deposited BAM files. ENA may also make conventional FASTQ available. If your objective is immediate alignment with a new reference, FASTQ may be convenient. If your objective is to preserve what the authors actually deposited, the submitted BAM has stronger archival significance.

The inventory lets you make that decision consciously.

## 6. Second use case: “I want a durable archive, and I do not have a special reason to prefer FASTQ”

This is the default `archival` policy.

You can ask what it would select without downloading anything:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --dry-run
```

Because you previously used `metadata`, the application does not need to retrieve the project again. It validates the local snapshot and constructs `manifest.tsv` from the existing inventory.

The default policy operates independently for each Run:

```text
original submitted files
        ↓ if unavailable
SRA representation
        ↓ if unavailable
ENA-generated FASTQ
```

The dry run tells you how many Runs use each representation, how many physical files that means, how many bytes are required, how much space the destination filesystem has, and why any fallback occurred.

This is the moment to notice a 2 TB mistake before it becomes a 2 TB download.

The resulting:

```text
manifest.tsv
```

has a very different meaning from `files.tsv`.

`files.tsv` says:

> These are the objects ENA reported.

`manifest.tsv` says:

> Given this explicit policy, these are the exact objects I have decided to acquire.

That distinction is the heart of the archive.

## 7. Third use case: “I am building an RNA-seq pipeline and specifically want conventional FASTQ”

For many computational workflows, what you actually want is not the depositor's native representation but ENA's standardized FASTQ.

Request it explicitly:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation fastq \
  --dry-run
```

The `fastq` policy is strict.

If every Run has ENA-generated FASTQ, the manifest can be built. If one Run does not, the command fails rather than quietly substituting a BAM, SRA object, or other representation.

That behavior is useful in pipelines. If a workflow expects FASTQ, discovering before execution that one sample exists only as a native BAM is preferable to receiving a heterogeneous input directory.

Once satisfied:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation fastq \
  --jobs 2
```

Do not confuse “FASTQ is convenient for my workflow” with “FASTQ is necessarily the object deposited by the authors”. They answer different questions.

---

## 8. Fourth use case: “I specifically need the files the authors deposited”

Use:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation submitted \
  --dry-run
```

This is useful when the exact submitted representation matters: archival preservation, methods reconstruction, pipeline archaeology, or comparing the depositor's object with repository-derived representations.

The policy is again strict. If submitted originals are unavailable for one Run, the application does not silently fall back.

This is particularly important for material that reached ENA through another INSDC partner. ENA may know about the Run but not hold the original object submitted to NCBI or DDBJ.

---

## 9. Fifth use case: “I need an SRA representation”

Some existing infrastructure is built around the SRA Toolkit or around SRA-format objects.

Use:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation sra \
  --dry-run
```

and, if the dry run is satisfactory:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation sra
```

As with the other explicit representation policies, there is no fallback.

This keeps a computational requirement—“my workflow expects SRA”—separate from an archival policy—“preserve the most original object available”.

---

## 10. Sixth use case: “I really do want every ENA representation”

Occasionally the redundancy is the point.

You may be testing repository conversions, comparing submitted BAM with generated FASTQ, validating archival transformations, or building a small reference dataset for infrastructure development.

Then:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation all \
  --dry-run
```

The `all` policy selects every complete available representation.

For an ordinary biological analysis this is usually wasteful. For a repository-methods question it can be exactly what you need.

The dry run is particularly important here because the same biological reads can occupy disk more than once.

---

## 11. Downloading for real

Once the dry run looks sensible:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --jobs 2 \
  --batch-attempts 3
```

`--jobs` controls simultaneous file transfers. More is not automatically better. Network bandwidth, repository responsiveness and disk I/O all matter.

Each file first appears as:

```text
filename.part
```

Only after the expected byte count and ENA MD5 agree is it atomically promoted to its final name.

If the connection disappears halfway through the night, rerun the same command:

```bash
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --jobs 2
```

Verified completed files are skipped. Suitable `.part` files resume.

That makes rerunning the command normal recovery behavior rather than an emergency measure.

Follow progress with:

```bash
tail -f "$OUTDIR/logs/download.log"
```

If some objects still fail after all retry passes:

```bash
cat "$OUTDIR/logs/failed_accessions.txt"
```

A project with one failed Run is not falsely reported as successfully complete.

## 12. Validate before giving the dataset to a pipeline

When acquisition finishes:

```bash
ena-project validate "$OUTDIR"
```

This is stricter than:

```bash
ena-project validate "$OUTDIR" --metadata-only
```

Full validation requires the sequence objects selected by the current manifest to exist and verifies their sizes and ENA MD5 checksums.

This is an excellent boundary between acquisition and analysis.

A Nextflow, Snakemake or ad hoc analysis should ideally consume a dataset that has already passed archive validation rather than discovering acquisition errors during alignment or variant calling.

## 13. Seventh use case: “I want to freeze the acquisition plan now and download later”

Suppose you are preparing data for a project meeting, asking an administrator to allocate storage, or handing acquisition to another machine. You already know the representation policy but do not want to start transferring data.

Use `snapshot`:

```bash
ena-project snapshot "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation archival
```

This performs the metadata acquisition and creates `manifest.tsv`, but downloads no sequence objects.

You can now send a colleague an exact description of:

```text
which project was queried
which metadata were returned
which representations existed
which objects the policy selected
how large those objects are
which MD5 values ENA advertised
```

Before handoff:

```bash
ena-project validate "$OUTDIR" --metadata-only
```

`snapshot` is therefore useful when the *decision* to acquire should become an explicit artifact before the bytes arrive.

## 14. Eighth use case: “The machine that chooses the data is not the machine that downloads it”

This is where an explicit manifest becomes useful.

Imagine that your laptop has internet access and is where you inspect the scientific metadata, while a large storage server performs the acquisition.

Create and validate the snapshot on the first machine, then transfer the acquisition unit—at minimum its metadata and manifest—to the destination.

On the destination machine:

```bash
ena-project download /path/to/manifest.tsv \
  --outdir "$OUTDIR"
```

The command treats the manifest as the acquisition contract and does not rediscover the project from ENA before downloading.

This is valuable for reproducibility: the second machine executes a previously made decision rather than making a new one.

Do not casually combine a manifest from one project with an archive directory belonging to another. Version 0.1.1 explicitly checks project and Study identity when an existing snapshot is present and refuses cross-project contamination.

## 15. Ninth use case: “I have the metadata but no network connection, and I want to reconsider the policy”

The representation decision itself does not require another ENA query.

Given:

```text
metadata/derived/files.tsv
metadata/derived/runs.tsv
```

you can construct a manifest offline:

```bash
ena-project manifest \
  "$OUTDIR/metadata/derived/files.tsv" \
  --representation fastq \
  --output "$OUTDIR/manifest.tsv"
```

This is useful on an isolated compute system, while travelling, or when preserving reproducibility requires you to work only from a previously captured repository snapshot.

It also demonstrates an important architectural point:

```text
repository evidence
        ↓
file inventory
        ↓
selection policy
        ↓
manifest
```

Selection is reproducible from the preserved evidence. It is not hidden inside the download operation.

## 16. Tenth use case: “Someone deleted a derived table, but the raw metadata are intact”

The raw ENA responses are the evidence. The TSV and JSON tables are interpretations that can be regenerated.

Use:

```bash
ena-project metadata-normalize \
  --metadata-dir "$OUTDIR/metadata"
```

No ENA request is needed.

This is useful after accidental deletion of a derived table, when checking determinism, or when reconstructing machine-readable tables from an archived snapshot.

For reproducibility work on an old archive, use the software release associated with that snapshot unless you are intentionally performing a schema migration.

---

## 17. Eleventh use case: “I archived this project six months ago. Has ENA changed?”

Repositories are living scientific infrastructure. Metadata can be corrected, accessions can gain annotations, and in unusual cases a referenced file can change.

Do not overwrite the old snapshot.

Refresh it:

```bash
ena-project snapshot "$PROJECT" \
  --outdir "$OUTDIR" \
  --refresh
```

The new metadata are first assembled and validated in staging. Only a coherent snapshot becomes current.

The previous state is retained beneath:

```text
metadata/archive/<snapshot-id>/
```

If ENA now advertises different content for a path where you already hold a file, the application distinguishes a valid historical repository object from a corrupt local file.

A valid old version can move beneath:

```text
superseded/<snapshot-id>/
```

before the new version is acquired.

That distinction is scientifically useful. “ENA changed the object” and “my disk contains corrupted bytes” are not equivalent events.

## 18. What should go into an analysis workflow?

After successful full validation, a computational pipeline usually needs only part of the archive.

For example, an RNA-seq Nextflow workflow may consume:

```text
fastq/
```

plus information from:

```text
metadata/derived/samples.tsv
metadata/derived/runs.tsv
```

That does **not** mean the remaining archive is disposable.

Keep:

```text
metadata/
files.tsv
manifest.tsv
logs/
```

with the downloaded files.

These explain where the analysis inputs came from.

The analysis repository itself should contain your workflow, parameters and scientific decisions—not another uncontrolled copy of the public source archive.

## 19. A compact routine for a newly discovered dataset

For a project you have just found in a publication, the cautious routine is:

```bash
PROJECT="PRJEB2772"
OUTDIR="/path/to/BIOPROJECTS/$PROJECT/sources/ena"

# 1. Learn what ENA actually contains.
ena-project metadata "$PROJECT" --outdir "$OUTDIR"

# 2. Check the snapshot before trusting it.
ena-project validate "$OUTDIR" --metadata-only

# 3. Read the biological and file metadata.
column -t -s $'\t' "$OUTDIR/metadata/derived/runs.tsv" | less -S
column -t -s $'\t' "$OUTDIR/metadata/derived/files.tsv" | less -S

# 4. Decide what representation you actually need.
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation archival \
  --dry-run

# 5. Acquire only after checking the dry run.
ena-project download "$PROJECT" \
  --outdir "$OUTDIR" \
  --representation archival \
  --jobs 2

# 6. Establish the integrity boundary before analysis.
ena-project validate "$OUTDIR"
```

For analysis-oriented work, replace:

```text
--representation archival
```

with:

```text
--representation fastq
```

only because you have consciously decided that standardized FASTQ is the representation your workflow requires.

## 20. The larger idea

Downloading public sequencing data is easy enough that it is tempting to treat acquisition as a disposable prelude to the “real” analysis.

For reproducible computational biology, it is better regarded as the first analytical boundary.

You need to know which biological objects you selected, which repository records described them, what physical files were offered, why one representation was preferred over another, and whether the local bytes still correspond to the repository's advertised checksums.

ENA Project Archiver therefore preserves several things that could have been collapsed into a single download script:

```text
raw metadata        what ENA returned
normalized metadata what those records mean operationally
files.tsv           what ENA made available
manifest.tsv        what you decided to acquire
sequence files      the verified local objects
```

That separation may seem elaborate when a project contains five Runs.

It becomes much less elaborate when the project contains five hundred, when an analysis needs to be repeated two years later, or when somebody asks the deceptively simple question:

> “Exactly which version of the public data did you analyse?”
